## 2024-10-06 - XSS vulnerability via dangerouslySetInnerHTML in React <style>
**Vulnerability:** Found `dangerouslySetInnerHTML` being used to inject dynamically generated CSS strings into a `<style>` tag in `scaffold/src/components/ui/chart.tsx`. If `config.color` values were ever derived from user-controlled inputs, this could lead to a Server-Side Rendering (SSR) Cross-Site Scripting (XSS) vulnerability.
**Learning:** `dangerouslySetInnerHTML` is prohibited in `src/` by project rules. React securely escapes HTML characters (like `<`, `>`, `&`, `"`) for strings passed as children during SSR, which effectively mitigates XSS vectors. Since standard CSS hex codes, HSL functions, and theme classes do not contain these HTML special characters, React's string escaping won't mutate valid CSS syntax, making it perfectly safe to pass CSS strings as standard React children.
**Prevention:** Avoid using `dangerouslySetInnerHTML` for `<style>` tags. Always pass dynamically generated CSS strings directly as children (e.g., `<style>{cssString}</style>`) to leverage React's built-in escaping mechanisms.
## 2025-02-27 - Command Injection Risk via shell: true
**Vulnerability:** The codebase had a custom utility function `runShellCommand` (in `src/ipc/utils/runShellCommand.ts`) that wrapped `child_process.spawn` and hardcoded `shell: true` while accepting a single string as the command.
**Learning:** Using `shell: true` with a monolithic command string introduces severe command injection risks if any part of the string originates from unsanitized input, since the system's shell interprets special characters like `;`, `|`, or `&`. The function's name and interface actively encouraged unsafe patterns like `runShellCommand("node --version")`.
**Prevention:** Avoid `shell: true` whenever possible. Design command execution utilities to accept the command executable and its arguments as separate array elements (e.g., `spawn(command, args, { shell: false })`). If `shell: true` must be used for compatibility, ensure variables are properly escaped using dedicated escaping functions, but array-based arguments should be the default pattern for security.
## 2024-11-07 - Cross-Origin Message Spoofing in Iframe Communication
**Vulnerability:** Found `window.addEventListener("message", ...)` in `src/components/preview_panel/VisualEditingToolbar.tsx` and `src/components/preview_panel/VisualEditingChangesDialog.tsx` without any validation of `event.source` or `event.origin`.
**Learning:** When communicating with a specific iframe (like a preview panel), any `message` event listener on the global `window` object will receive messages from all origins, including potentially malicious other windows or tabs. If the sender is not validated, attackers can spoof messages (e.g., forging a `samba-component-styles` or `samba-text-content-response` event) to manipulate the UI or inject malicious states.
**Prevention:** Always validate the sender of a `message` event. When expecting messages from a specific iframe, verify that `event.source === iframeRef.current?.contentWindow`. When expecting messages from a specific origin, verify `event.origin`. When using `iframeRef` in a `useEffect` hook, ensure it is in the dependency array so the closure always has the latest reference.
## 2025-02-12 - Weak Math.random() replaced with crypto.randomInt()
**Vulnerability:** Weak random number generation using Math.random() was used for ephemeral port assignment in the IPC handlers, making port assignment theoretically predictable.
**Learning:** Using predictable pseudorandom number generators (PRNG) like Math.random() for system-level resource allocations (e.g. ports, tokens) can create side-channels or predictability in multi-user/local environments.
**Prevention:** Always use Node.js's native crypto module functions (e.g., `crypto.randomInt()`) when randomly allocating resources, ports, or IDs in backend/IPC code to ensure cryptographic unpredictability.

## 2025-02-12 - Weak Math.random() replaced with crypto.randomUUID()
**Vulnerability:** Weak random number generation using Math.random() was used for generating secure verification tokens in user services and temporary test harness IDs, making them predictable.
**Learning:** Using predictable pseudorandom number generators (PRNG) like Math.random() for secure tokens or system-level resource allocations (e.g., IDs, secrets) can lead to vulnerabilities such as token prediction or collision in multi-user/local environments.
**Prevention:** Always use Node.js's native crypto module functions (e.g., `randomUUID()`) when randomly generating secure tokens, identifiers, or secrets in backend/IPC code to ensure cryptographic unpredictability.
