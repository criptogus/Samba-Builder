## 2024-10-06 - XSS vulnerability via dangerouslySetInnerHTML in React <style>
**Vulnerability:** Found `dangerouslySetInnerHTML` being used to inject dynamically generated CSS strings into a `<style>` tag in `scaffold/src/components/ui/chart.tsx`. If `config.color` values were ever derived from user-controlled inputs, this could lead to a Server-Side Rendering (SSR) Cross-Site Scripting (XSS) vulnerability.
**Learning:** `dangerouslySetInnerHTML` is prohibited in `src/` by project rules. React securely escapes HTML characters (like `<`, `>`, `&`, `"`) for strings passed as children during SSR, which effectively mitigates XSS vectors. Since standard CSS hex codes, HSL functions, and theme classes do not contain these HTML special characters, React's string escaping won't mutate valid CSS syntax, making it perfectly safe to pass CSS strings as standard React children.
**Prevention:** Avoid using `dangerouslySetInnerHTML` for `<style>` tags. Always pass dynamically generated CSS strings directly as children (e.g., `<style>{cssString}</style>`) to leverage React's built-in escaping mechanisms.
## 2025-02-27 - Command Injection Risk via shell: true
**Vulnerability:** The codebase had a custom utility function `runShellCommand` (in `src/ipc/utils/runShellCommand.ts`) that wrapped `child_process.spawn` and hardcoded `shell: true` while accepting a single string as the command.
**Learning:** Using `shell: true` with a monolithic command string introduces severe command injection risks if any part of the string originates from unsanitized input, since the system's shell interprets special characters like `;`, `|`, or `&`. The function's name and interface actively encouraged unsafe patterns like `runShellCommand("node --version")`.
**Prevention:** Avoid `shell: true` whenever possible. Design command execution utilities to accept the command executable and its arguments as separate array elements (e.g., `spawn(command, args, { shell: false })`). If `shell: true` must be used for compatibility, ensure variables are properly escaped using dedicated escaping functions, but array-based arguments should be the default pattern for security.
## 2025-03-01 - Missing origin validation on window message event listeners
**Vulnerability:** `window.addEventListener("message", ...)` handlers in `VisualEditingChangesDialog.tsx` and `VisualEditingToolbar.tsx` were processing postMessage events without validating the source or origin.
**Learning:** When a generic `message` listener does not check `event.source` or `event.origin`, any iframe or window can send messages triggering internal UI logic.
**Prevention:** Always validate `event.source` matches the expected `iframe.contentWindow`, or that `event.origin` matches the trusted application origin.
