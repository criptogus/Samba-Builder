# O que aprender com o DeepSeek Harness (`dsh`) para o Samba Builder

> Análise feita em 2026-09-08 a partir de evidência direta do repositório
> [`deepseek-ai/deepseek-harness`](https://github.com/deepseek-ai/deepseek-harness) (branch `master`): README,
> árvore de `packages/`, `docs/` e READMEs de 8 grupos de pacotes. Nada aqui foi implementado; cada item aponta
> o que muda no nosso roadmap (`plans/kilocode-parity-plan.md`, requisitos em `docs/PRODUCT_MEMORY.md`).

## O que o projeto é (fatos, não impressão)

- `dsh` = **agent harness open-source da DeepSeek**, "everything is a plugin", construído sobre **Cordis**
  (framework IoC/plugin). Monorepo pnpm, TypeScript, MIT, ~226k estrelas, preview de desenvolvedor com
  quebras de compatibilidade anunciadas.
- Roda como **Web UI local**: `npx @deepseek-ai/dsh web` sobe em `127.0.0.1:3080` (com `--no-open`).
- **`packages/` é uma lista de capacidades**, não de telas: `skill`, `workflow`, `guard`, `goal`, `todo`, `plan`,
  `subagent`, `compaction`, `spill`, `sandbox`, `browser-use`, `computer-use`, `mcp`, `lsp`, `acp`, `extensions`,
  `jobs`, `schedule`, `webhook`, `api-gateway`, `session`, `session-query`, `storage`, `llm`, `identity`,
  `credentials`, `workspace`, `web`, `client`, `core`, `host`, `boot`, `bundle`, `util`, `ptc-runtime`, `typert`.
- Cada grupo se divide em **plugins pequenos** ao redor de uma **seam** explícita: `ctx.skills`, `ctx.tools`,
  `ctx.commands`, `ctx.goals`, `ctx.workflowEngine`, `ctx.spillStore`, `ctx.attachments`, `ctx.llm`.
- Documentação **gerada do código**: `docs/capability-seams.md` traz o aviso
  `Generated by scripts/gen-doc-graphs.ts - do not edit by hand`, e existem `tool-catalog.md`,
  `config-catalog.md`, `module-graph.md`, `graph-atlas.md`, `persistence-catalog.md`, `dependency-catalog.json`.

## Onde ele já está onde nós estamos indo

## O que vale copiar (por ordem de retorno)

### A. Guardas de higiene de loop — `REQ-20` (novo, P1, ~2–3 dias)

Não depende de nenhuma fase do roadmap e o nosso loop já sofre dos dois padrões:

- **Chamada repetida idêntica** → avisar o modelo para mudar de abordagem ou concluir (temos "no-progress
  signature" só para `run_tests`; falta o caso geral).
- **Timeout por tool** quando ela declara limite, devolvendo erro claro em vez de sessão pendurada.

**Aceite:** Given o mesmo nome+input de tool repetido N vezes sem mudança de estado, Then o turno recebe um aviso
explícito e o evento aparece no log/UI. Given uma tool que declara `timeoutMs`, Then ela falha com erro
recuperável dentro do limite.

### B. Fechar o `REQ-03` como o `dsh` faz — catálogo no prompt + registry (P0, ~3–4 dias)

- Publicar na sessão um **catálogo ordenado** (nome, descrição, escopo, `modes`) em vez de o modelo precisar
  chamar a tool só para descobrir. É exatamente a parte que ficou pendente no `REQ-03`.
- Evoluir a descoberta para um **registry de catálogos** com **formato único** por nome e precedência única
  (projeto > usuário > futuro plugin). Isso é o alicerce do `REQ-12` (marketplace além de MCP).
- **Watch** das pastas: hoje a UI só atualiza com o botão "Atualizar".

**Aceite:** Given um `.samba/skills/<nome>/SKILL.md` novo, Then ele aparece no catálogo da sessão sem reiniciar.
Given duas fontes com o mesmo nome, Then vence uma só e o motivo é registrado.

### C. Spill em vez de truncar — `REQ-22` (novo, P2, ~3–4 dias)

Nós truncamos saídas grandes (`AGENT_READ_FILE_TRUNCATION_NOTICE`, `bounded_text_file`) e o resto se perde.
O `dsh` guarda o texto completo, devolve **preview + localizador** e mantém o original quando o storage falha.
Isso conversa direto com o aviso de contexto que acabamos de corrigir: menos tokens presos, nada perdido.

**Aceite:** Given uma tool que devolve 2 MB, Then o modelo recebe preview + caminho do arquivo íntegro e
consegue ler o trecho que precisar; Given falha de escrita, Then o resultado original é entregue mesmo assim.

### D. Catálogos gerados do código — `REQ-23` (novo, P2, ~2–3 dias)

O `dsh` gera `tool-catalog`, `config-catalog`, `capability-seams`, `module-graph`. Nós mantemos a lista de tools
em `tool_definitions.ts`, a prosa em `docs/agent_architecture.md` e as estimativas em
`estimateAgentToolTokens` — três lugares que já podem divergir (e divergem na prática ao adicionar uma tool).

**Aceite:** Given `npm run gen:catalogs` (novo), Then `docs/tool-catalog.md` e um grafo de seams são gerados do
código; CI falha se o arquivo commitado estiver desatualizado.

### E. Workflow como script — evolução do `REQ-04` (P2, mapear na Fase 3)

O `workflow` do `dsh` é o passo além do comando declarativo: **script de orquestração escrito pelo modelo** que
distribui trabalho para subagentes num sandbox e devolve um valor. Nós já temos as duas peças
(`execute_sandbox_script` + subagentes) — falta a seam. Registrar como `REQ-24` no escopo da Fase 3.

### F. Refinar o `REQ-08` (goal) com a lição de separação

Manter a decisão de **um objetivo durável por sessão** (estado), com o **motor de continuação separado e opt-in**
(`goal-round-driver`), e `/goal` atendido pelo app **sem gastar turno do modelo**, como no `dsh`.

## O que **não** copiar

- **Web-UI-first com servidor local (`dsh web` na 3080).** Nosso produto é desktop com preview do app do usuário;
  virar um servidor web muda a proposta, não a incrementa.
- **Adotar Cordis como runtime.** O ganho seria conceitual e o custo, reescrever o núcleo. Copiamos as **ideias**
  (seam explícita, famílias pequenas, catálogos gerados), não o framework.
- **Dinâmica de plugins em memória (`extensions/`) agora.** É poderoso e é Fase 4+: exige versionamento imutável,
  política de arquivos e cartões de ciclo de vida antes de virar ferramenta do modelo.
- **Preview de desenvolvedor com quebras anunciadas** como norma: nosso público é não-técnico e precisa de previsibilidade.

## Infra de qualidade que vale espiar (barato e mensurável)

- Configs de teste **separadas por preocupação** (`vitest.web.config`, `vitest.web-stress`, `vitest.web.perf`,
  `vitest.bench`) — nós temos uma suíte; perf/stress separados tornariam regressão de desempenho visível.
- `.jscpd.json` (detecção de duplicação) e `snapshots/` versionados.
- `SAFETY.md` (postura de segurança do agente) como artefato próprio — útil para conversa enterprise, e nós já
  temos a substância espalhada em `docs/security.md` e no prompt de revisão.
- Docs com **i18n de verdade** (`README.md` + `README.zh.md` + `*.i18n.yaml` como memória de tradução).
